## Problem Statement

When a destination IIS (in this case CT WebIZ at `ctwiz-test.dph.ct.gov`) returns a
`SecurityFault` back to IZ Gateway Hub (Onboarding), Hub logs the fault exception but
**never writes the `transactionData` log entry**. As a result, the transaction is invisible
to Kibana searches on any `transactionData.*` field (source facility, destination, etc.).
The event can only be found by eventId or timestamp — which requires prior knowledge of
those values.

The original fix in IGDD-2125 addressed this for `checkRetries()` in `MessageSender`.
That method was later refactored; the fix is present in the current code but the bug
has recurred, suggesting the root cause is not (only) in `setProcessError`.

## Hypotheses Remaining to Investigate

In priority order:

1. **`HubClientFault.isRetryable()` for CORRECT_MESSAGE** (line 113 of HubClientFault.java)
   — If it returns `true`, retries happen but eventually `setProcessError` is called.
   The missing log entry would then be caused by something else entirely.
   If it returns `false`, the fault exits `canRetry()` immediately, `setProcessError` is
   called on the first attempt, and the issue is downstream of that.

2. **JSON serialization of TransactionData containing a SecurityFault processError**
   — The fault's `detail` field contains the full HL7 IIS response with raw `\r`
   characters and potentially hundreds of characters. If Jackson throws during
   `Markers2.append("transactionData", this)` serialization, the logstash-logback-encoder
   may silently drop the log event. Check the logback configuration for any
   `SuppressWarnings` or error handlers on the appender.

3. **`RequestContext` ThreadLocal state at the time `logIt()` is called**
   — Check if any code path between the fault being thrown and `logIt()` clears or
   replaces the TransactionData in the RequestContext ThreadLocal. Specifically look at
   `AccessControlValve.invoke()` → `RequestContext.getRoles().clear()` in its `finally`
   block — though this is unlikely to affect TransactionData.

4. **`setProcessError` not being called at all**
   — Add a debug log or breakpoint at `TransactionData.setProcessError()` to confirm
   it's being invoked for the SecurityFault case. If it's not called, `hasProcessError`
   stays `false` — which would not explain the missing log entry but would explain why
   the transaction isn't surfacing as a failure.

## IGDD-2125 Root Cause (for reference)

The original fix added `RequestContext.getTransactionData().setProcessError(f)` to
`MessageSender.checkRetries()` for the non-retryable fault branch. That method was later
refactored into `canRetry()`, and the fix was carried forward. The fix affects what is
**stored** in transactionData, but does not explain why the `logIt()` call itself produces
no Elasticsearch document.

## Next Steps on Resume

1. Open `HubClientFault.java` and read `isRetryable()` at line 113.
2. Check what `RetryStrategy.CORRECT_MESSAGE` maps to for retryability (look at
   the `RetryStrategy` enum or wherever `isRetryable()` is defined on the base `Fault` class).
3. Confirm whether `computeTransactionTimes()` or the `getMessage()` call in `logIt()`
   can throw for this fault type.
4. Check the logback appender configuration in the hub (`src/main/resources/`) for any
   error handling that could silently suppress the INFO log from TransactionData.
5. After identifying root cause, determine fix: likely in `LoggingValve`,
   `LoggingValveBase`, or `TransactionData.logIt()` to ensure the transaction log is
   always written regardless of the type of process error.
